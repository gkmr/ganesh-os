Inside the Ganesh OS fleet

Most of what the fleet does is not thinking, it is moving text between four places. Thirty-seven scheduled Claude sessions write files; one Apps Script is the only thing allowed to touch Telegram. This is the path a single message takes in each direction, what can refuse it, and the one place where the rules are enforced rather than hoped for.

01 · The three layers

Only one of them can say no

Why the prompt-only version keeps failing

Every defect of Sep 4 to 8 was a rule that lived in a prompt: a weekday typed from memory, a file created as a Google Doc, a folder read by the wrong id. Prompts are advice. A lane that misreads one produces a confident wrong message. Moving a rule into the relay guard is the whole fix; the prompt then only has to make the redirect graceful.

LayerWhat it doesWhy it sits where it sits
Relay guardIntercepts every queued file before Telegram sees it: refuses Doc-typed and binary content, holds stale backlog out of MAIN, locks overlapping ticks, dedupes repeats, self-heals the reply cursorThe only layer with authority. If a lane ignores every law in its prompt, the wrong file still never reaches you, and the OPS line names the lane and the fix.
Relay scriptsCourier the outbox, poll the inbox, keep the sent-log and mirror, chunk and escape, map message ids to tasks, read the Supra board server-sideKeeps tokens, cursors and transport out of every lane's reach. A lane writes a file and exits; it never handles the send.
Prompt lawsFleet common law and per-lane laws: folder ids, date truth, plain-text writes, footer shape, no legendsAdvisory by design. They make a lane do the right thing the first time so the guard rarely fires; when a lane drifts, the system degrades to a dead-letter, not to a wrong message.

02 · What stays manual

Four things the fleet is not allowed to do

Stated on purpose, not discovered later

The boundaries are drawn where a wrong action is expensive or irreversible. Each has a cheap path around it.

Not automatedThe reasonWhat happens instead
Direct Telegram from a laneOne bot, one cursor. A second reader silently steals every reply; a token in a prompt ends up in a logLanes write files to the outbox or POST to the relay; the relay alone talks to Telegram and keeps the audit trail
Sending iMessageOnly the Mac can send it; cloud has no routeLanes write a .txt into imessage-outbox; a Mac task sends it and writes a .sent marker. Until that task runs, the file waits
Deploying the relayIt is your Google account and the URL every lane holds; a new deployment changes the URLYou paste the versioned file and publish a new version of the existing deployment; the first tick posts a 🛠 proof line
Model changes and parking stale tasksBoth change what you pay for or what you see, on your word onlyThe fleet reports and proposes; it never pins a model or parks a task without "pin them" or "park it" from you

A lane is configuration, not infrastructure

Each lane is a prompt on a cron with a few connectors. It runs in a fresh session with no servers to keep alive and no keys to hold. Its whole memory is the fleet folder: a marker file at start, a marker file at the end, and the mirror as the record of what actually reached you.

The file that saves the most

Every message is a file with a sibling marker. x.tgmsg.delivered reading "ok" is the only proof of delivery; a lane's own "sent" is not. When a message seems missing, the marker and the mirror answer in one read, and the gap report answers the reverse question: did your reply reach the relay at all.

Why the bill is the point

Five Opus lanes cost as much as the other thirty combined and do work a cheaper model does the same. The relay tick costs nothing. So the economics push the same direction as the reliability: put judgment in a few lanes, put enforcement in the relay, and let everything else be plain text moving between folders.
